**Состояние:** реального алгоритма пока нет. `app/packing/stub.py` воспроизводит
фиксированные demo-снимки; он не подбирает коробки и не доказывает оптимальность.

Протокол структурный: наследоваться от него не требуется. Вход и результат —
dataclasses из `app.domain.models`, без Pydantic, FastAPI, HTTP, PostgreSQL и ORM.
`create_app(settings, engine=implementation)` позволяет проверить подключение
без изменения API. Default factory пока выбирает DemoPackingEngine; переключение
на настоящее ядро выполняет интегратор после готовности агента.

## Задачи Packing Engine Engineer

1. Прочитать `CONTRACTS.md`. Не менять поля/статусы/единицы без интегратора.
2. Развернуть товары в физические ItemInstance с устойчивыми id.
3. Реализовать объяснимую детерминированную эвристику, уникальные ортогональные
   ориентации, непересечение, границы, вес и остатки. Не использовать black-box ядро.
4. Приоритеты: меньше неуложенных единиц, меньше коробок, меньше пустой объём,
   более простая последовательность ручной укладки. Документировать tie-break.
5. Возвращать метрики, причины для каждой неуложенной единицы и, если найдены,
   близкие полноценные альтернативы с учётом options.
6. Пронумеровать placements по выполнимому порядку укладки. Сервис генерирует
   инструкции из этих placements; движок может оставить instructions пустыми.
7. Добавить тесты в `backend/tests/packing/`: границы/касания/пересечения,
   повороты, запрет вращения, вес, нулевые остатки, частичный результат,
   повторяемость, независимость от порядка входных массивов, количественный баланс.

Владение: `backend/app/packing/**`, `backend/tests/packing/**`, этот документ.
Общие модели остаются под управлением интегратора.

## Ограничения foundation

Все четыре fixture-плана размещают товары на дне, поэтому не моделируют опору
и устойчивость многоуровневой укладки. Товары — жёсткие параллелепипеды без зазоров,
деформаций, хрупкости и ограничений нагрузки сверху. Физическую исполнимость,
сложность укладки и ограничения времени будущей эвристики агент должен описать явно.
Нельзя обозначать неудачу эвристики как доказательство невозможности размещения.

Demo-fixtures остаются примерами контракта и UI. Будущий движок не обязан повторять
их размещения побайтно: корректность и ограничения проверяются отдельно.
