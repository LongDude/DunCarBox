# DunCarBox — рабочее место упаковщика

Frontend MVP использует React, TypeScript, Vite, React Three Fiber и Three.js.
Главный экран — план упаковки: оператор выбирает коробку, берёт указанный экземпляр
товара, ориентирует его по размерам и выполняет шаги укладки. Все DTO и единицы
соответствуют [CONTRACTS.md](CONTRACTS.md); backend API не изменён.

## Запуск и источники данных

Из `frontend/` с Node.js 24 и npm:

```sh
npm ci
npm run dev
npm run test
npm run build
npm run test:e2e
```

В PowerShell можно использовать `npm.cmd` вместо `npm`. Dev-сервер доступен на
`http://127.0.0.1:5173`; `/api` проксируется на `127.0.0.1:8000`. Production build
проверяет TypeScript и создаёт `frontend/dist/`. Docker/nginx сохраняет относительные
пути `/api/v1`; адрес API не зашивается в UI. Для браузерных проверок нужен Chromium,
указанный в конфигурации Playwright.

По умолчанию приложение использует **серверный API**. Выбор «Демо без сервера»
в шапке или `http://127.0.0.1:5173/?mode=demo` включает автономную демонстрацию.
`VITE_DATA_SOURCE=demo` задаёт начальный режим при запуске Vite или сборке;
`?mode=api` явно возвращает серверный режим. Автоматического переключения источника
при ошибке сети нет. При смене источника рабочая область создаётся заново:
черновик и показанный результат относятся только к выбранному источнику.

Единый адаптер `src/api/dataSource.ts` предоставляет одинаковые методы для обоих
режимов: health, сценарии, расчёт и CRUD коробок. Компоненты не содержат mock
placements. Автономный режим воспроизводит четыре канонических сценария:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Простой заказ | Все товары в одной коробке |
| Несколько коробок | Все товары в двух коробках, разные ориентации |
| Товар не помещается | Нет упакованных товаров, причина по размерам |
| Нехватка коробок | Частичная упаковка с объяснением остатка |

Сопоставление учитывает все поля коробок и товаров, не зависит от порядка строк
или ключей JSON и применяет настройки альтернатив. Изменённый валидный запрос
получает `ENGINE_NOT_IMPLEMENTED`; клиент не рассчитывает новую укладку сам.
Маркер `DEMO_STUB` и версия `demo-stub-v1` сохраняются в ответах, а экран явно
показывает «ДЕМО-ПЛАН». Сервер, работающий со stub, также отмечается в интерфейсе.

Исходные JSON находятся в `demo/`. Для независимой сборки Docker их точные копии
включены в `frontend/src/features/demo/fixture-data/`. После изменения исходных
fixtures обновите копии из корня репозитория:

```powershell
Copy-Item demo/*.json frontend/src/features/demo/fixture-data/
```

`fixtures.test.ts` сравнивает каждый JSON побайтно с каноническим файлом. Эта
проверка пропускается только в отдельно скопированном frontend без корневого
`demo/`; проверки DTO остаются доступны.

## Основной рабочий процесс

1. В «Каталоге коробок» создайте типы с внутренними размерами, допустимым весом
   товаров и остатком. Записи можно изменить и удалить; удаление подтверждается
   на карточке. Код сохранённой коробки остаётся неизменным.
2. В «Заказе» укажите номер и товары: название, длину, ширину, высоту, вес одной
   единицы, количество и разрешение поворота. Строки можно добавлять, дублировать
   и удалять. Новая строка получает фокус; Tab переводит к следующему полю.
3. Для презентации выберите сценарий и нажмите «Загрузить демо-заказ»: товары и
   снимок коробок заполнятся автоматически. «Использовать коробки из каталога»
   явно заменяет снимок сценария текущим каталогом.
4. Нажмите «Рассчитать упаковку». На время операции показаны загрузка и skeleton,
   повторная отправка заблокирована; доступна отмена. Ответ открывает план.
5. Выберите коробку и выполняйте инструкцию. Ссылка «К инструкции» прокручивает
   страницу прямо к рабочей области. После закрытия перейдите к следующей
   коробке. При необходимости выберите альтернативу, экспортируйте JSON или PDF.

Каталог и снимок заказа независимы. В серверном режиме каталог хранится в
PostgreSQL. В автономной демонстрации CRUD сохраняется в `localStorage` с ключом
`duncarbox.demo.catalog.v1`; если браузер запрещает запись, изменения доступны
до конца текущего сеанса. Загрузка сценария не меняет остатки каталога. Расчёт
не резервирует и не списывает коробки. Нулевые остатки передаются в запросе;
пустой каталог допустим как предметное ограничение заказа.

Результат хранится вместе с копией `boxes/products/options` и номером заказа.
Изменение черновика, настроек, номера или используемого каталога помечает прежний
план устаревшим и предлагает пересчёт. Запоздалые ответы отменённых запросов
не заменяют текущие данные. История и серверное сохранение черновика не предусмотрены.

## Ввод, ограничения и ошибки

В полях указаны единицы: целые миллиметры, граммы и штуки. Вес в кратких сводках
отображается в килограммах; исходный DTO остаётся в граммах.

| Поле или ограничение | Допустимое значение |
| --- | --- |
| Размеры | 1–100 000 мм |
| Вес единицы и максимальный вес коробки | 1–100 000 000 г |
| Остаток коробки | Неотрицательное целое |
| Количество товара в строке | Положительное целое |
| Типы коробок / строки товаров | Без прежних пределов 100 / 200 |
| Все физические единицы заказа | Без прежнего предела 1 000; целые числа должны точно представляться в JavaScript |
| Название | 1–200 символов после удаления крайних пробелов |
| Идентификатор | 1–64 символа по шаблону контракта, уникален внутри списка |

Числовые строки, дроби, NaN, бесконечности и булевы значения вместо чисел
отклоняются. Ошибки показываются возле полей и в сводке; первое некорректное поле
получает фокус. API details вида `body.products.0.length` превращаются в подписи
«Товар 1 · Длина, мм» и русские сообщения. Диагностическое сообщение API сохраняется.
Отдельно обрабатываются конфликт идентификатора, удалённая запись, HTTP-ошибка,
некорректный JSON/DTO, отсутствие сети и таймаут 15 секунд для коротких запросов.
Все расчёты используют фоновые задачи: ограничения 120 секунд на вычисление нет.
Отмена прекращает ожидание и останавливает серверный расчёт с дочерними процессами.
UI предлагает повторить
действие и не выводит traceback или внутренние сетевые детали.

## Экран результата

Сводка показывает статус, использованные коробки, упакованные и неупакованные
единицы, заполнение, вес уложенных товаров без тары и число операций. Заполнение
берётся из `metrics.fill_ratio`: это отношение суммарного объёма товаров к
суммарному объёму использованных коробок, а не среднее процентов карточек.
Число операций включает подготовку и закрытие каждой коробки.

Карточка коробки содержит тип, внутренние размеры, заполнение, текущий/допустимый
вес, число товаров и слоёв. Выбранная коробка определяет сцену и инструкцию справа.
Товар обозначен названием и номером экземпляра; цвет стабилен между коробками
и планами. Текущий экземпляр получает контур, подпись и текст инструкции — цвет
не является единственным обозначением состояния.

Раздел сравнения свёрнут по умолчанию и показывает рекомендованный план и максимум
три альтернативы в порядке API. Выбор одновременно переключает метрики, коробки,
инструкции, проблемы, печать и экспорт. UI не пересчитывает оценку плана,
не придумывает «сложность» и не называет вариант оптимальным: этих полей нет в v1.

## Инструкции и шаги

Порядок, ссылки на товары и геометрия приходят из серверных `instructions` и
`placements`. Для коробки с N товарами:

- `0 / prepare_box`: коробка пустая, оператор проверяет тип и размеры.
- `1..N / place_item`: видны первые k товаров; товар шага k выделен, будущие скрыты.
- `N+1 / close_box`: показаны все товары, оператор сверяет количество/вес и закрывает коробку.

«Назад», «Следующий шаг», список операций и «Показать всё» используют одно
состояние шага. Из обзора можно вернуться к шагу. При смене коробки или альтернативы
показ начинается с подготовки. Автопоказ двигается с интервалом 2,8 секунды,
останавливается на закрытии, при ручном переходе или скрытии вкладки.

Основная подсказка объясняет ориентацию словами: какая из уже ориентированных
сторон идёт вдоль длины, в глубину и вверх. Пространственное пояснение в
`presentation.ts` читает фактическую геометрию: передний левый угол, касание соседа
справа при совпадающих передних гранях и высоте или расстояния от стенок и дна.
Опора на конкретные товары не предполагается без данных. Это объяснение координат,
а не новый packing engine.

Исходный текст сервера всегда доступен в «Точных координатах и инструкции сервера»
и остаётся текстом печатных шагов. Там же доступны x/y/z, размеры после поворота
и код ориентации. DTO и серверная последовательность не изменяются.

## Геометрия 3D и слои

Начало координат — передний левый нижний внутренний угол. Доменная ось x направлена
вправо, y вглубь, z вверх. Единственное преобразование `domainToScene` в
`src/three/geometry.ts` отображает `(x, y, z)` в `(x, z, -y)`.

```text
scale = 6 / max(1, box.length, box.width, box.height)
center = scale × (x + length/2, z + height/2, -(y + width/2))
mesh size = scale × (length, height, width)
```

Используются `Placement.dimensions`: поворот уже применён движком и второй раз
не выполняется. Общий scale применяется к коробке, товарам и позициям при рендеринге;
исходные миллиметры и относительная геометрия сохраняются. Камера охватывает коробку
с учётом пропорций canvas; доступны поворот, приближение и сброс вида. Передняя
грань явно обозначена. Товары используют общий `InstancedMesh`, рендеринг идёт
по требованию; тяжёлый 3D-модуль загружается при открытии результата.

«По слоям» группирует товары по одинаковому `position.z` — высоте нижней грани.
Это вид сверху на размещения слоя, без произвольного сечения объёмов. Передняя
сторона находится снизу SVG; масштаб соответствует коробке. Шаг автоматически
выбирает слой текущего товара, слой также переключается вручную. Легенда и SVG
доступны с клавиатуры. Отсутствие WebGL2, ошибка Canvas или потеря контекста
переключают на этот вид; инструкции и управление шагами остаются доступны.

## Проблемные состояния

`partial` сохраняет доступный план и отдельно показывает неуложенные экземпляры,
связанные причины и карточки диагностики. При `impossible` пустая сцена заменяется
объяснением и переходом к редактированию. Размеры, вес, остаток и отсутствие
коробок имеют отдельные понятные подписи.

`NO_FEASIBLE_PLACEMENT` отображается как «Алгоритму не удалось найти корректное
размещение при текущих ограничениях»; заголовок также не утверждает доказанную
физическую невозможность. `DEMO_STUB` показан заметным маркером плана и сохраняется
в JSON и печатных пояснениях.

## Печать и экспорт

JSON сохраняет номер заказа, исходный снимок запроса, полный исходный результат,
`selected_plan_id` и выбранный план. Исходный ответ не подменяется альтернативой.

«Печать / PDF» использует браузерную печать и отдельную разметку с `@media print`.
Она содержит номер заказа, выбранный план, метрики, все коробки с размерами и
содержимым, полный список серверных шагов и проблемные единицы с причинами.
Печать не зависит от выбранного шага или видимой коробки. Навигация, интерактивные
контролы и WebGL-canvas не требуются для чтения бумажной инструкции.

## Проверки и границы интеграции

Vitest проверяет API→UI преобразования, статусы и issues, выбор альтернатив,
экспорт, координаты, центры кубоидов, масштаб, шаги, слои, framing, стабильность
цветов, ввод, API-ошибки, отмену запросов и соответствие fixtures. Актуальные
результаты тестов, браузерного прогона и build — в [AGENT_HANDOFF.md](AGENT_HANDOFF.md).

Frontend подключён к `/api/v1` с `DeterministicPackingEngine` по умолчанию.
Реальные сценарии и изменённые заказы проверены через production nginx → API →
PostgreSQL. Отдельные live E2E включаются флагом DUNCARBOX_LIVE_E2E=1; автономный
demo продолжает явно показывать статические планы. При добавлении Z3 options и
metadata расширены обратно совместимо; placements и инструкции имеют прежний формат.

## Выбор алгоритма

В форме заказа доступны «1 · Быстрая эвристика» и «2 · Оптимизатор Z3».
При выборе Z3 появляются время поиска и число параллельных процессов без
потолков 60 секунд и 8. Используется не больше доступных серверу ядер.
Сохранённые настройки восстанавливаются из localStorage; загрузка демо-заказа
с сервера не сбрасывает выбор. Изменение настроек помечает предыдущий план устаревшим.
В автономном demo выбор выключен и подписан «Готовый демо-план»; переход обратно
на сервер восстанавливает предпочтения, fixture не выдаётся за новый расчёт Z3.

Блок «Алгоритм и качество решения» показывает выбранный и фактический алгоритм,
доказанный оптимум / допустимый план / резервную эвристику и причину остановки.
Z3 и его резерв требуют 100% опоры; обычная эвристика — минимум 80%.
Пределы модели 16 предметов / 64 слота сняты. При таймауте интерфейс явно
сообщает об отсутствии доказательства оптимальности.
Метаданные сохраняются в JSON и печати. Отметка optimal относится к основному
плану, а не автоматически к любой выбранной альтернативе.

В серверном списке демо есть обычный «Большой заказ: 10 000 предметов · 100 видов ·
8 типов коробок». Кнопка загрузки заполняет 100 строк по 100 единиц и снимок коробок,
сохраняя выбранный алгоритм. Расчёт выполняется в фоне без фиксированного общего
лимита времени, с отображением прошедшего времени и отменой серверного процесса.
Для результата показываются 12 карточек коробок на странице и выбор по номеру.
Полная печатная инструкция большого заказа создаётся только при печати, а JSON
содержит все размещения. Автономный режим сохраняет четыре готовых примера.
