# Нагрузочный тест: 10 000 предметов, 100 видов, 8 типов коробок

Это один большой заказ: 100 SKU по 100 экземпляров. У всех SKU различные размеры
и масса; у 25 видов запрещены повороты. В каталоге восемь разных размеров коробок
с разными лимитами веса, по 1250 экземпляров каждого типа. Все единицы физически
упаковываемы: каждый предмет помещается в любую пустую коробку, а суммарный запас
позволяет в крайнем случае использовать одну коробку на предмет.

Данные генерируются по фиксированным формулам без случайности. JSON и SHA-256
записываются для воспроизводимости. Заказ не разбивается на маленькие партии и
не уменьшается до лимитов движка. Используется настоящий dispatcher и сервис
инструкций с их штатными настройками.

## Запуск

Из `backend/`, после `uv sync --frozen`:

```sh
uv run python -m app.packing.stress_benchmark --timeout-seconds 600
```

Выходные файлы по умолчанию находятся в `.cache/stress-10000/heuristic/` от корня:

- `request.json` — входные 100 SKU и восемь типов коробок;
- `report.json` — статус, время, параметры, сведения о машине и метрики при успехе;
- `result.json` — полный результат с placements и инструкциями, только при успехе.

Для другого каталога: `--output ../.cache/my-stress-run`.
Один каталог рассчитан на один запуск; для одновременных запусков задавайте разные
каталоги. Повторный запуск заменяет эти файлы и удаляет старый result.json.

Только получить исходный JSON:

```sh
uv run python -m app.packing.stress_benchmark --generate-only
```

Проверить сохранённый режим выбора Z3:

```sh
uv run python -m app.packing.stress_benchmark --algorithm z3 --timeout-seconds 600
```

Пределы модели 16 предметов / 64 слота сняты. Z3 сначала строит резерв с полной
опорой, затем пытается построить и решить SMT-модель за выбранное время. Для
10 000 предметов это обычно приводит к `fallback/time_limit`, без доказательства
оптимальности. Отчёт содержит фактический исход, не требует заранее фиксированного
`size_limit` и не выдаёт резерв за результат SMT.

Обычная эвристика сохраняет штатные 12 стратегий и опору 80%; резерв Z3 —
2 стратегии, 64 точки и опору 100%. Это разные алгоритмические настройки:
сравнивать времена как ускорение одной и той же модели некорректно.

## Проверки и границы

Успешный тест требует ровно 10 000 упакованных единиц и отсутствие неуложенных.
Независимый валидатор проверяет уникальность экземпляров, все quantities,
размеры/повороты, пересечения, опору, вес, остатки, метрики, последовательность
шагов и соответствие инструкций placements, включая альтернативы. Дополнительно
проверяется, что исходный заказ не изменён.

Весь расчёт, генерация инструкций, проверка и запись результата выполняются
в отдельном процессе. `--timeout-seconds` ограничивает этот полный запуск, включая
резервную эвристику Z3; процесс останавливается и освобождается. Код выхода:
0 — проверки пройдены, 124 — таймаут, 1 — ошибка или прерывание. Таймаут не
считается успешным тестом и не создаёт фиктивный result.json. Короткий прогон
проверяет ограничение времени; он не доказывает способность упаковать заказ.

CLI обращается к движку напрямую, без HTTP и PostgreSQL. Тот же заказ доступен
из меню **Сервер → Демо-сценарий → Большой заказ: 10 000 предметов…**. Загрузите
демо, выберите алгоритм и нажмите «Рассчитать упаковку». Это обычный демо-заказ;
его план каждый раз рассчитывается через фоновый API. Лимит HTTP в 1000 единиц снят.
Число CPU записывается как
характеристика машины; обычная эвристика не становится многопроцессной от запуска
на многоядерной машине. Для честного измерения выполняйте benchmark без конкурирующих
нагрузок. Время конкретного прогона не является гарантией производительности.

## Pytest

В быстрой suite проверяются генератор, разнообразие данных, физическая разрешимость,
сохранение API-лимита и завершение процесса по deadline. Сам тяжёлый тест пропускается
без явного флага:

```powershell
cd backend
$env:DUNCARBOX_RUN_STRESS_10000 = '1'
$env:DUNCARBOX_STRESS_TIMEOUT = '600'
$env:DUNCARBOX_STRESS_ALGORITHM = 'heuristic'
uv run pytest tests/packing/test_stress_10000.py -q -s
```

Linux/macOS:

```sh
DUNCARBOX_RUN_STRESS_10000=1 DUNCARBOX_STRESS_TIMEOUT=600 \
  uv run pytest tests/packing/test_stress_10000.py -q -s
```

Pytest создаёт отчёт и результат в своём временном каталоге. CLI удобнее для
сохранения измерений на хакатонной машине. Фактические прогоны фиксируются в
[AGENT_HANDOFF.md](AGENT_HANDOFF.md).

## Фактический прогон после pull

На текущей Windows-машине с Python 3.12.13 и 16 логическими CPU:

| Режим | Лимит | Результат |
|---|---:|---|
| heuristic, штатные настройки | 120 с | timeout, план не завершён |
| z3 → резерв с полной опорой | 120 с | 10 000/10 000, 346 коробок, заполнение 35.55%, 88.969 с, валидация пройдена |

Это исторические измерения до снятия предела размера Z3. Вторая строка — успешная упаковка эвристическим резервом с `fallback/size_limit`,
а не доказанный SMT-оптимум для 10 000 предметов. Выходные артефакты находятся
в `.cache/stress-10000/`; этот каталог не коммитится. Полная штатная эвристика
за 120 секунд не уложилась, для её полного прогона предусмотрен больший лимит.
