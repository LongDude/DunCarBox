# Алгоритм 2: Z3

`Z3PackingEngine` дополняет существующую эвристику. Он использует `z3-solver`
(версия закреплена в `backend/uv.lock`) и модель, адаптированную из пользовательского
`test_code.py`. Исходный файл сохранён; backend не исполняет его CLI и не зависит
от его местоположения. REST, PostgreSQL, placements, 3D и генератор инструкций общие
для обоих алгоритмов.

## Выбор и настройки

В серверном режиме выберите «Z3» в форме заказа. Пример API:

```json
{
  "boxes": [{"id":"box","name":"Коробка","length":200,"width":100,"height":100,"max_weight":1000,"available_count":1}],
  "products": [{"id":"item","name":"Товар","length":100,"width":100,"height":100,"weight":100,"quantity":2,"allow_rotation":true}],
  "options": {"algorithm":"z3","solver_workers":4,"include_alternatives":false}
}
```

Без новых полей работает прежний `heuristic`. Z3 работает без ограничения времени,
до доказательства оптимальности, ошибки решателя или отмены пользователем.
`solver_timeout_ms` устарело: по умолчанию null; положительные значения из старых
заказов принимаются, но не ограничивают поиск. Число процессов —
положительное целое без потолка 8, по умолчанию 4. Настройки сохраняются при загрузке
демо-заказа с сервера. Автономный режим воспроизводит fixtures и не запускает Z3.

## Модель и целевая функция

Каждый физический предмет имеет номер коробочного слота (либо -1 для неуложенного),
целочисленные x/y/z и одну из разрешённых ориентаций. Условие allow_rotation=false
сохраняет исходную ориентацию. Координаты — минимальный угол, единицы — мм и г.

- Предметы внутри своей коробки и не пересекаются; касание допустимо.
- Суммарный вес не превышает лимит. Каждая открытая коробка содержит предметы,
  число экземпляров типа не превышает доступный остаток.
- Предмет на дне либо **100% его основания** покрыто верхними гранями ранее
  размещённых предметов. Допускается совместная опора на несколько предметов;
  зазоры и свесы запрещены. Это строже стандартной эвристики с порогом 80%.
- Неуложенные предметы не создают коллизий или фиктивных опор. Все единицы входят
  ровно в один из списков placements/unpacked_items.

Приоритеты `Optimize` лексикографические:

1. Максимум количества упакованных единиц.
2. При равенстве — максимум объёма этих товаров.
3. Затем минимум суммарного объёма коробок: максимальное общее заполнение
   при том же количестве и объёме товаров.
4. Затем минимум количества коробок.

Цены из test_code.py не перенесены: в текущем каталоге цен нет. Частичная упаковка
разрешена вместо отказа от всего заказа. Штрафы за высоту/удобство и механические
нагрузки не входят в доказательство оптимальности. Все предметы — жёсткие
параллелепипеды; центр масс, прочность, хрупкость и траектория загрузки не моделируются.

Модель содержит не более **N коробочных слотов на весь заказ**, где N — сумма
quantity. Тип каждого слота выбирается переменной из совместимого каталога;
остатки ограничивают число слотов каждого типа. Запас из 1000 коробок не
разворачивается в 1000 переменных экземпляров. Неиспользуемые слоты пусты.
Слоты нумеруются по первому назначенному предмету; одинаковые единицы товара
упорядочены по слоту и координатам. Это убирает перестановки равнозначных планов,
сохраняя представителя каждой допустимой упаковки.
Пары, превышающие вес или объём любой доступной коробки, сразу разводятся по
разным слотам. Если все товары уже упакованы резервом и ни одна пара не может
делить коробку, канонические номера слотов фиксируются: каждому товару нужна
своя коробка. Типы коробок при этом по-прежнему выбирает оптимизатор.

Полная опора добавляется **по мере обнаружения нарушений**. В начальной модели
есть только необходимое условие: предмет на дне или касается перекрывающейся
верхней грани другого предмета в той же коробке. Для каждого кандидата точный
геометрический проход находит зазор в объединении опорных прямоугольников.
Зазор задаёт символическую контрольную точку: край основания или правый/дальний
край опоры. Добавляется требование покрытия этой точки во всех размещениях,
где она находится внутри основания. Сетка по миллиметрам не используется.

Решатель прерывается для добавления новых ограничений и продолжает поиск.
Ограничения добавляются только после выхода из check(), не внутри callback.
Каждое из них необходимо для полной опоры и не исключает допустимую упаковку.
Число возможных контрольных точек конечно. Доказанный оптимум ослабленной модели,
прошедший независимый полный валидатор, оптимален и для исходной задачи.
Таким образом, качество и доказательство сохраняются. В худшем случае всё ещё
могут потребоваться O(N³) точечных ограничений с O(N) возможными опорами каждое.

Фиксированных пределов **16 предметов / 64 слота нет**. Неподходящие типы в модель
не попадают, но остаются в исходном запросе и диагностике. На больших заказах
доказательство оптимальности всё ещё может занимать значительное время.

## Время, ядра и резервный результат

До запуска Z3 строится валидный резервный план эвристикой с полной опорой:
2 стратегии, 64 точки, без альтернатив. Он даёт нижнюю границу качества поиска;
Z3 ищет план не хуже по тем же четырём целям. Подготовка резерва, ожидание свободного
процесса, построение модели и оптимизация не ограничены временем. Отмена проверяется
в циклах эвристики и контроллере Z3; она завершает задачу без выдачи частичного
резерва за законченный расчёт.

Размещения резерва передаются как начальные подсказки Z3, без фиксации координат.
Если резерв уже упаковал все предметы, их упаковка становится обязательной:
первые две цели уже доказаны. Только в этом случае суммарный объём его коробок V
ограничивает объём нового плана, число слотов — величиной floor(V/min_box_volume),
а число коробок каждого типа T — floor(V/volume(T)). Типы с объёмом больше V
можно исключить. Для частичного резерва такие ограничения не применяются:
большая коробка может позволить уложить больше товаров.

После выбора плана для каждой коробки проверяются два порядка товаров с полной
опорой. Принимается только более компактная укладка, сохранившая все назначенные
предметы. Если места не хватило, сохраняется исходная укладка, сдвинутая к передней левой
стенке целиком, без изменения взаимных опор. Эта стадия не меняет цели Z3.

Портфель запускается через multiprocessing `spawn`: отдельный Z3 Context и
изолированные процессы, разные варианты поиска, только обычные структуры Python в IPC.
Контроллер передаёт улучшенные проверенные оценки всем процессам через ограниченные
неблокирующие очереди. Процессы принимают их между вызовами check() и в callback
новых моделей; во втором случае поиск прерывается и граница добавляется после check().
Новые границы включают равенство, поэтому в модели остаётся допустимый план.
Собственные найденные улучшения также сохраняются при добавлении ограничений опоры.
Если во время длительного доказательства нет новых callback, получение чужой
оценки откладывается до возврата check(). Передача оценок не задаёт лимит времени.
После получения доказательства или отмены оставшиеся процессы останавливаются
и освобождают ресурсы. При завершении всех процессов без доказательства возвращается
лучший проверенный план с `reason=solver_error`.
Число процессов ограничено доступными CPU (affinity, если поддерживается),
а не константой 8. Можно выбрать 10, 16 и больше. Синхронные вызовы делят семафор
внутри API-процесса; отдельная фоновая задача имеет свой контроллер. Штатный Compose
использует один процесс API и допускает один активный фоновый расчёт.
Ускорение не обязано быть линейным, а маленьким заказам часто достаточно 1–2 процессов.

Каждый полученный от решателя план независимо проверяется общим валидатором
с min_support_ratio=1. Лучший допустимый план используется в результате.
Резервная эвристика обрабатывает весь заказ — единицы не обрезаются.
Все расчёты браузера выполняются через фоновый API с прогрессом этапа и временем.
На этапе поиска Z3 `progress=null`: доля выполненного доказательства неизвестна.
Отмена передаётся контроллеру Z3,
который завершает свои процессы до остановки фонового задания.

## Что означает результат

`status=success/partial/impossible` по-прежнему говорит о количестве уложенных
товаров. Отдельное `optimization` объясняет качество доказательства:

| status | Значение |
|---|---|
| optimal | Совпали доказанные границы всех четырёх целей; либо предварительная проверка доказала отсутствие любых допустимых предметов. Основной план оптимален в описанной модели |
| feasible | Получен допустимый план, оптимальность не доказана |
| fallback | Использован резервный эвристический план, оптимальность не доказана |

`reason`: completed / solver_error (`time_limit` и `size_limit` читаются для старых
результатов). Ответ `unknown` или отсутствие доказанных границ целей означает
solver_error, а не невозможность упаковки. `time_limit_ms=null`. `workers` показывает число
запущенных процессов (0 при пропуске Z3), `support_ratio=1.0`. `algorithm_version`
обозначает Z3 pipeline; status=fallback явно раскрывает фактический источник плана.
Пустой список альтернатив допустим: текущий Z3 pipeline возвращает один основной план.

Доказательство целей не означает уникальность координат. Параллельный поиск
может дать другую равнозначную укладку на иной машине. Эвристические планы
воспроизводимы при одинаковых настройках;
поле calculation_seconds закономерно меняется между запусками.
Инструкции всегда генерируются из возвращённых placements и проверяются вместе с ними.

## Реализация и проверка

- `backend/app/packing/dispatcher.py`: выбор алгоритма.
- `backend/app/packing/z3_constraints.py`: компактная модель, симметрии, подсказки и границы.
- `backend/app/packing/z3_support.py`: точный поиск зазоров и ограничения опоры.
- `backend/app/packing/z3_model.py`: цикл уточнения Optimize, извлечение и валидация.
- `backend/app/packing/z3_engine.py`: резерв, отмена и управление процессами.
- `backend/tests/packing/test_z3*.py`: опора, цели, ориентации, stock/weight, отмена и совместимость старых таймаутов.
- `test_z3_refinement.py`: сравнение с полной моделью без симметрий, внутренние
  зазоры, компактные слоты, границы полного/частичного резерва и обмен оценками.
- `backend/tests/test_algorithm_api.py`: переключение, четыре demo, инструкции, отсутствие таймаута.
- Frontend unit/E2E: параметры запроса, подписи результата и реальные запросы Z3.

Для backend нужен PostgreSQL, как и в README: `uv run pytest`,
`uv run ruff check app tests`. Z3 устанавливается обычным `uv sync --frozen` и
включается в production Docker image.

Замер подготовки модели на Windows (Z3 4.16.0.0, Python 3.13.5, без эвристического
резерва и без check()): одинаковые предметы 2×2×2, коробка 10×10×10, остаток 1000.
На 12 предметах прежняя/новая модель строилась за 1,732/0,244 с, на 20 —
13,324/0,327 с. Новая модель на 70 предметах: 3,433 с и 8365 утверждений вместо
заранее создаваемых 343000 ограничений одной только опоры в прежней реализации.
Это измерение подготовки на синтетическом входе, не обещание такого же ускорения
полного расчёта или конкретного пользовательского заказа. Лог worker содержит
время построения, общее время, число итераций/ограничений опоры и статистику Z3.

Дополнительный контроль на Python 3.12.10: 70 предметов 10×10×10 и 1000 коробок
10×10×10 одного типа. Подготовка резерва, модели и поиск дали доказанный оптимум
за 2,922 с: 70/70 предметов, 70 коробок, 100% заполнения. Это простой случай
взаимно несовместимых пар; результат не характеризует сложную смешанную укладку.

Проверка сохранения качества включает сравнение четырёх целей с исходной
реализацией из Git на 12 детерминированных малых заказах: оценки совпали.
Итоговая проверка на Python 3.12.10: `pytest -q` — 409 passed, 1 stress skipped;
`ruff check app tests`, форматирование изменённых Python-файлов и
`git diff --check` прошли. API-тесты использовали отдельный временный PostgreSQL.
