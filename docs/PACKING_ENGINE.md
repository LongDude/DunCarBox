# Packing Engine

Реализован `app.packing.engine.DeterministicPackingEngine`, версия
`candidate-packing-v1`. Ядро использует стандартную библиотеку Python и domain
dataclasses, без HTTP, PostgreSQL, UI, случайности и внешнего packing solver.
Общие модели и [CONTRACTS.md](CONTRACTS.md) не изменены.

## Подключение

```python
from fractions import Fraction
from app.packing import DeterministicPackingEngine, EngineOptions
from app.services.packing import PackingService

engine = DeterministicPackingEngine()
result = PackingService(engine).pack(request)

# Настройки ядра; не изменение HTTP PackingOptions:
strict_engine = DeterministicPackingEngine(
    EngineOptions(min_support_ratio=Fraction(1, 1), max_candidate_points=256)
)
```

Протокол остаётся `pack(PackingRequest) -> PackingResult`. Ядро возвращает
`instructions=()`; существующий PackingService генерирует русские инструкции
для основного плана и альтернатив. `create_app(settings, engine=engine)` позволяет
интегратору подключить реализацию. Default app factory продолжает использовать
DemoPackingEngine: переключение относится к отдельному интеграционному этапу.

## Алгоритм

1. Товары разворачиваются по product.id, затем численному индексу: `A:1`, `A:2`.
   Контрактный разделитель — двоеточие. Единицы неделимы.
2. Вычисляется совместимость товара с каждым типом коробки по разрешённым
   ориентациям и весу. Нулевые остатки сохраняются для диагностики.
3. Выполняется до 12 фиксированных стартов с разными порядками товаров и
   правилами выбора коробок. Совпадающие пары порядок/правило пропускаются.
4. На каждом шаге пробно заполняются доступные типы коробок оставшимися товарами.
   Выбирается один непустой вариант, уменьшается локальный остаток.
5. Каждый законченный план независимо валидируется. Лучший план и до трёх
   различных альтернатив проверяются ещё раз перед возвратом.

Это эвристика: нет полного перебора порядков, миллиметровой сетки или
доказательства оптимума. Заполнение коробки жадное; размещённые товары внутри
старта не перемещаются. Другие старты пробуют другие решения.

## Геометрия и ориентации

Координаты строго по CONTRACTS: x вправо/length, y вглубь/width, z вверх/height;
origin — передний левый нижний внутренний угол. Position — минимальный угол
товара. Размеры/координаты — целые мм, масса — целые граммы.

`unique_orientations` выдаёт пары `(код, Dimensions)` в порядке
`LWH,LHW,WLH,WHL,HLW,HWL`, сохраняя только первую для каждого уникального набора
размеров. При запрете вращения остаётся LWH.

`fits_inside_box`, `placement_inside_bounds`, `aabb_intersects` — чистые функции.
Коллизия требует строго положительного пересечения по всем трём осям. Касание
граней, рёбер и углов разрешено. Граница коробки и вес ровно на пределе допустимы.
Epsilon не используется.

## Candidate points

Пустая коробка имеет точку `(0,0,0)`. Размещение `(x,y,z)` размером `(dx,dy,dz)`
добавляет `(x+dx,y,z)`, `(x,y+dy,z)`, `(x,y,z+dz)`. Удаляются duplicates,
точки вне коробки и внутри занятых полуоткрытых объёмов. На максимальной внешней
грани нельзя начать товар положительного размера.

Для первых max_candidate_points допустимых углов добавляются проекции к ближайшим
препятствиям/стенам в отрицательном направлении каждой оси, а также обе
последовательности x/y. Так находятся дополнительные полезные пересечения
поверхностей без декартова произведения координат. Полный AABB и support затем
проверяются для реального предмета в каждой ориентации.

Порядок точек: `(z,x+y,x,y)`, после чего применяется лимит. Координатное dominance
само по себе небезопасно: более удалённая точка может иметь другую опору или
вести в другую полость. Удаление всего, доминируемого origin, уничтожило бы
укладку поверх товаров. Безопасное сокращение — совпадения, занятые точки и
границы; cap явно ограничивает полноту эвристики.

## Опора

На z=0 всю нижнюю грань поддерживает дно. Выше дна берутся только верхние грани
товаров, заканчивающиеся **точно** на текущем z. Их пересечения с нижней гранью
объединяются sweep по x и объединением интервалов y: область считается один раз.
`support_area` возвращает целую площадь, `support_ratio` — справочную дробь.

Hard constraint сравнивает целые площади с числителем и знаменателем порога.
Default — `Fraction(4,5)` (80%). EngineOptions принимает порог в `(0,1]`, включая
Fraction или десятичное `0.8`, нормализуемое через десятичную запись. Настройка
не разрешает полностью висящие предметы.

Это упрощение: центр масс, прочность товара, нагрузка сверху, хрупкость,
зазоры и движение руки/предмета не моделируются. Во входном контракте нет этих
данных. Покрытие 80% не доказывает механическую устойчивость для произвольной массы.

## Порядки товаров и выбор коробок

Портфель включает объём по убыванию; максимальный размер/объём; вес/объём;
доступную площадь основания/объём; дефицит подходящих коробок/объём/вес;
вес и объём по возрастанию. Последний вариант помогает упаковать больше единиц,
когда один крупный товар вытесняет несколько маленьких. Tie-break всегда
product_id и численный unit_index.

Шесть порядков используются с максимизацией числа единиц в пробной коробке;
ещё шесть стартов пробуют smallest-first, fill-first и максимальный упакованный
объём. Точные комбинации явно перечислены в STRATEGIES.

Перед локальной оценкой коробки считается число оставшихся единиц, которым после
расходования её экземпляра не останется ни одного подходящего типа в остатке.
Меньшее число предпочтительно: это помогает сохранить универсальную коробку
для сложного товара. Проверка оптимистическая и не решает совместное распределение
геометрии/веса всех будущих коробок. После неё применяется правило старта, затем
box.id. Fill сравнивается точным Fraction. Пустые коробки не открываются; stock
не превышается. До трёх проходов по пропущенным товарам используют опору,
появившуюся после более поздних размещений.

## Scoring и complexity

Сначала проверяются границы, коллизии, вес и опора. Затем минимизируется:

```text
(z, resulting_bounding_height, -contact_area, occupied_envelope_volume,
 x+y, orientation_index, x, y, length, width, height)
```

Контакт — площадь касания стен/дна/крышки и уже размещённых товаров. Объём
охватывающего параллелепипеда — простая оценка компактности, а не точное измерение
фрагментации свободного пространства. При прочих равных предпочтительна первая
допустимая ориентация контрактного порядка.

Глобальное сравнение лексикографическое:

```text
(unpacked_count, -packed_volume, box_count, empty_volume,
 packing_complexity, usage_of_fully_depleted_types, canonical_layout_signature)
```

Число единиц имеет безусловный приоритет. При равном числе сохраняется больший
объём товаров. Улучшение fill или числа коробок не вытесняет более полный план
**из найденных**; это не гарантия полноты поиска. При равной полноте меньший
empty_volume означает лучший общий fill. Stock — последний содержательный tie-break.

`packing_complexity` возвращает компоненты и их простую сумму: шаги размещения +
дополнительные уровни z + предметы выше дна + смены ориентации между соседними
шагами. Нет скрытых весовых коэффициентов. Метрика не добавлена в общий DTO.

## Инструкции и relationships

Placements сортируются по `(z,x,y,product_id,unit_index)` и получают шаги 1..N.
Каждая опора имеет строго меньший z: это топологический порядок зависимостей.
Валидатор проверяет опору только среди ранее уложенных предметов.

`placement_relationships(box.placements)` возвращает внутренние dataclasses:
item_instance_id, on_floor, supported_by, right_of, behind. Это прямые контакты
граней для генерации «на дно», «поверх», «справа», «за». Сервис получает все
позиции/шаги и может использовать helper. Дополнительного JSON metadata нет:
действующий контракт не предусматривает такого поля.

## Диагностика и альтернативы

- NO_BOX_TYPES: типы коробок не заданы.
- ITEM_TOO_LARGE: ни одна разрешённая ориентация не входит ни в один тип,
  включая stock=0. Это доказуемое ограничение размеров.
- ITEM_TOO_HEAVY: вес единицы выше предела всех геометрически подходящих типов.
- BOX_STOCK_EXHAUSTED: нет остатка подходящих по размеру и весу коробок.
  Исходный stock=0 — доказуемое ограничение; если коробки потрачены текущим
  планом, сообщение явно допускает другое перераспределение товаров.
- NO_FEASIBLE_PLACEMENT: поиск не нашёл вариант при своих правилах и лимитах.
  Также дополняет исчерпание stock текущим планом. Это не доказательство
  невозможности другого размещения.
- PARTIAL_PACKING: агрегирующее предупреждение при частично упакованном заказе.

Контрактный статус impossible означает «не размещена ни одна единица», а не
самостоятельное доказательство. Источник вывода нужно читать из issues.
Каждая неуложенная единица связана с русским объяснением; issues сгруппированы
и отсортированы по коду/id.

Альтернативы — разные найденные планы с тем же числом и объёмом упакованных
товаров. Signature игнорирует порядок открытия коробок и перестановки единиц
одного product. Разный тип коробки или реальная геометрия считается отличием.
Возвращается максимум min(request.options.max_alternatives,
EngineOptions.max_alternatives, 3). Отключение alternatives не сокращает поиск
рекомендованного плана. Финальный порядок строго контрактный: unpacked count,
box count, empty volume, id. Искусственные копии и заведомо менее полные планы
не предлагаются.

## Детерминизм, performance и ограничения

Нет времени, UUID или случайного seed в результате. Перестановка boxes/products
и Python hash seed не меняют результат. Все caches и остатки принадлежат одному
вызову; повторные/параллельные вызовы не меняют запрос или склад. Нестандартные
EngineOptions кодируются в algorithm_version, чтобы различие настроек было явным.

Defaults: 128 candidate points, 12 starts, 3 fill passes, 3 alternatives.
Максимумы: 4096 точек, 12 стартов, 10 проходов, 3 альтернативы.
Request-local LRU хранит до 128 пробных заполнений. Одинаковые геометрии коробок
и последовательности единиц переиспользуют результат. Неудачная одинаковая форма
не проверяется повторно до изменения коробки. Отсечение более высоких z и худшей
bounding height сохраняет точный порядок score.

Большой заказ с множеством SKU и 100 типами коробок может быть дорогим: число
пробных заполнений зависит от типов, стартов и числа открытых коробок. Нет
wall-clock timeout, который сделал бы результат зависимым от CPU. Интегратор
может уменьшить лимиты при жёстком latency budget. Cap может скрыть полезные
верхние точки за бесполезными нижними. Нет гарантии оптимума, полноты поиска,
доступа рукой или свободной траектории загрузки.

## Проверки и benchmark

`validate_solution(request, result, min_support_ratio)` самостоятельно
восстанавливает единицы и проверяет AABB/union опоры отдельной реализацией.
Проверяются уникальность, quantities, ориентации, границы, stock, вес, метрики,
шаги, причины и distinct alternatives. Нарушение вызывает PackingValidationError,
а не маскируется предметным статусом.

Из backend:

```text
python -m pytest tests/packing tests/test_demo_fixtures.py -q
python -m app.packing.benchmark --repeat 2
python -m app.packing.benchmark --repeat 2 --stress
```

Benchmark: четыре demo-запроса, многоуровневые кубики, смешанные размеры, предел
веса и дефицит универсальной коробки. Stress добавляет 216 одинаковых и 120
смешанных единиц. Вывод: items, packed, boxes, fill, elapsed ms, issues. Время
измеряется снаружи результата; повторы сравнивают весь результат и инварианты.
Фактические измерения/команды текущего этапа — в AGENT_HANDOFF.md.

## Предложения интегратору по контракту

Публичный API не изменён. Найдены расхождения с новыми требованиями:

1. PackingOptions содержит только alternatives. Если порог нужен каждому HTTP
   запросу, согласованно добавить min_support_ratio=0.8 в domain/schema/TypeScript.
   Пока он задаётся внутренним EngineOptions при создании ядра.
2. Строка CONTRACTS «устойчивость пока не моделируется» описывает foundation.
   При интеграции уточнить: реализована минимальная опорная площадь, полноценной
   механической модели нет.
3. Для передачи relationships/complexity отдельными полями согласовать DTO;
   сейчас доступны чистые backend helpers.
4. Не переименовывать impossible молча: UI должен пояснять статус через issues.
   Менее категоричное имя можно обсудить при будущем пересмотре контракта.
