# Алгоритм 2: Z3

`Z3PackingEngine` дополняет существующую эвристику. Он использует `z3-solver`
(версия закреплена в `backend/uv.lock`) и модель, адаптированную из пользовательского
`test_code.py`. Исходный файл сохранён; backend не исполняет его CLI и не зависит
от его местоположения. REST, PostgreSQL, placements, 3D и генератор инструкций общие
для обоих алгоритмов.

## Выбор и настройки

В серверном режиме выберите «Z3» в форме заказа. Пример API:

```json
{
  "boxes": [{"id":"box","name":"Коробка","length":200,"width":100,"height":100,"max_weight":1000,"available_count":1}],
  "products": [{"id":"item","name":"Товар","length":100,"width":100,"height":100,"weight":100,"quantity":2,"allow_rotation":true}],
  "options": {"algorithm":"z3","solver_timeout_ms":10000,"solver_workers":4,"include_alternatives":false}
}
```

Без новых полей работает прежний `heuristic`. Таймаут Z3: 1–60 секунд,
по умолчанию 10; процессов: 1–8, по умолчанию 4. Настройки сохраняются при загрузке
демо-заказа с сервера. Автономный режим воспроизводит fixtures и не запускает Z3.

## Модель и целевая функция

Каждый физический предмет имеет номер коробочного слота (либо -1 для неуложенного),
целочисленные x/y/z и одну из разрешённых ориентаций. Условие allow_rotation=false
сохраняет исходную ориентацию. Координаты — минимальный угол, единицы — мм и г.

- Предметы внутри своей коробки и не пересекаются; касание допустимо.
- Суммарный вес не превышает лимит. Каждая открытая коробка содержит предметы,
  число экземпляров типа не превышает доступный остаток.
- Предмет на дне либо **100% его основания** покрыто верхними гранями ранее
  размещённых предметов. Допускается совместная опора на несколько предметов;
  зазоры и свесы запрещены. Это строже стандартной эвристики с порогом 80%.
- Неуложенные предметы не создают коллизий или фиктивных опор. Все единицы входят
  ровно в один из списков placements/unpacked_items.

Приоритеты `Optimize` лексикографические:

1. Максимум количества упакованных единиц.
2. При равенстве — максимум объёма этих товаров.
3. Затем минимум использованных коробок.
4. Затем минимум их суммарного объёма (эквивалентно пустоте при том же наборе товаров).

Цены из test_code.py не перенесены: в текущем каталоге цен нет. Частичная упаковка
разрешена вместо отказа от всего заказа. Штрафы за высоту/удобство и механические
нагрузки не входят в доказательство оптимальности. Все предметы — жёсткие
параллелепипеды; центр масс, прочность, хрупкость и траектория загрузки не моделируются.

Полная опора проверяется символически в потенциальных углах непокрытых участков:
граница основания и правые/дальние границы поддерживающих поверхностей. Сетка по
каждому миллиметру не строится, но число выражений растёт примерно как N⁴.
Поэтому полная модель допускает максимум **16 физических предметов и 64 полезных
коробочных слота**. Для каждого совместимого типа достаточно min(stock,N) слотов.
Неподходящие типы в модель не попадают, но остаются в исходном запросе и диагностике.

## Время, ядра и резервный результат

До запуска Z3 строится валидный резервный план эвристикой с полной опорой:
2 стратегии, 64 точки, без альтернатив. Он даёт нижнюю границу качества поиска;
Z3 ищет план не хуже по тем же четырём целям. Подготовка резерва и финальная
валидация добавляются ко времени, указанному для Z3; это не жёсткий SLA всего HTTP.

Портфель запускается через multiprocessing `spawn`: отдельный Z3 Context и
изолированные процессы, разные варианты поиска, только Python dataclasses в IPC.
При истечении общего срока процессы останавливаются и освобождают ресурсы.
Количество процессов ограничено CPU и общим лимитом до 8 workers **на процесс API**.
При нескольких Uvicorn workers этот лимит умножается; штатный Compose использует один.
На машине с 10 ядрами можно выбрать 8 процессов, оставив ресурсы API, БД и браузеру.
Ускорение не обязано быть линейным, а маленьким заказам часто достаточно 1–2 процессов.

Каждый полученный от решателя план независимо проверяется общим валидатором
с min_support_ratio=1. Лучший допустимый план используется в результате.
При превышении размера весь заказ обрабатывает резервная эвристика — единицы
не обрезаются. Она тоже может занимать заметное время на больших заказах.

## Что означает результат

`status=success/partial/impossible` по-прежнему говорит о количестве уложенных
товаров. Отдельное `optimization` объясняет качество доказательства:

| status | Значение |
|---|---|
| optimal | Совпали доказанные границы всех четырёх целей; либо предварительная проверка доказала отсутствие любых допустимых предметов. Основной план оптимален в описанной модели |
| feasible | Получен допустимый план, оптимальность не доказана |
| fallback | Использован резервный эвристический план, оптимальность не доказана |

`reason`: completed / time_limit / size_limit / solver_error. Таймаут или unknown
никогда не подменяется доказательством невозможности. `workers` показывает число
запущенных процессов (0 при пропуске Z3), `support_ratio=1.0`. `algorithm_version`
обозначает Z3 pipeline; status=fallback явно раскрывает фактический источник плана.
Пустой список альтернатив допустим: текущий Z3 pipeline возвращает один основной план.

Доказательство целей не означает уникальность координат. Параллельный поиск с
таймаутом может дать другую равнозначную укладку или успеть найти другое качество
на иной машине. Побайтовая воспроизводимость прежней эвристики сохранена отдельно.
Инструкции всегда генерируются из возвращённых placements и проверяются вместе с ними.

## Реализация и проверка

- `backend/app/packing/dispatcher.py`: выбор алгоритма.
- `backend/app/packing/z3_model.py`: ограничения, Optimize, извлечение и валидация.
- `backend/app/packing/z3_engine.py`: резерв, лимиты и управление процессами.
- `backend/tests/packing/test_z3*.py`: опора, цели, ориентации, stock/weight, deadline.
- `backend/tests/test_algorithm_api.py`: переключение, четыре demo, инструкции, fallback.
- Frontend unit/E2E: параметры запроса, подписи результата и реальные запросы Z3.

Для backend нужен PostgreSQL, как и в README: `uv run pytest`,
`uv run ruff check app tests`. Z3 устанавливается обычным `uv sync --frozen` и
включается в production Docker image.

Первичная документация: [Optimize API](https://z3prover.github.io/api/html/classz3py_1_1_optimize.html),
[приоритеты целей](https://microsoft.github.io/z3guide/docs/optimization/combiningobjectives/),
[Context и потоки](https://z3prover.github.io/api/html/classz3py_1_1_context.html).
